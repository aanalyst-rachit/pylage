Current system proves:

```text

 ↓

 ↓

 ↓

```

But it does **not yet fully implement**:

```text
State
 ↓
Dependency Graph
 ↓
Affected Components
 ↓
Dirty Nodes
 ↓
Scheduler
 ↓
Minimal Diff
 ↓
Minimal Patch
```

Therefore current system proves:

> **A known state update can reach the browser.**

It does not yet prove:

> **PySkin can automatically determine the smallest affected UI region.**

That is the next architectural challenge.

# 23. 🔥 PHASE 2.1 — REACTIVE SEMANTICS

Before implementing a dependency graph, formally define:

```text
What does reactive=True mean?
What does reactive=False mean?

When is State dependency registered?

What happens if the same State appears
in multiple components?

What happens when a component is removed?

What happens when State is replaced?

When is an update suppressed?

When is an update emitted?
```

Required contract:

```text
PropDefinition
      ↓
reactive=True
      ↓
runtime participates in dependency tracking
```

The metadata must become actual runtime behavior.

---

# 24. 🔥 PHASE 2.2 — DEPENDENCY GRAPH

Target model:

```text
State A
   │
   ├────► Component X
   │
   └────► Component Y

State B
   │
   └────► Component Z
```

When:

```python
state_a.set(...)
```

runtime should identify:

```text
X
Y
```

and leave:

```text
Z
```

untouched.

This is the central fine-grained reactivity mechanism.

---

# 25. 🔥 PHASE 2.3 — DIRTY NODE TRACKING

Introduce a runtime dirty set:

```text
dirty_nodes
```

Example:

```text
dirty_nodes = {
    component_123,
    component_456,
}
```

Only affected nodes enter the update pipeline.

Target:

```text
State change
      ↓
Dependency graph
      ↓
Affected components
      ↓
dirty_nodes
```

---

# 26. 🔥 PHASE 2.4 — UPDATE SCHEDULER

Introduce explicit scheduling.

Target:

```text
State changes
      ↓
mark dirty
      ↓
schedule update
      ↓
process dirty nodes
      ↓
emit updates
```

The scheduler must eventually support batching.

Example:

```python
count.set(1)
count.set(2)
count.set(3)
```

Potential target:

```text
3 immediate network messages ❌
```

Instead:

```text
one scheduled update
final state = 3
```

But batching behavior must be measured and tested rather than assumed.

---

# 27. 🔥 PHASE 2.5 — BATCHING

Target:

```text
Multiple synchronous State changes
                ↓
           dirty set
                ↓
          one flush cycle
                ↓
       final effective updates
```

Questions to establish:

```text
What is a flush boundary?

Immediate?
Microtask-like?
Explicit batch?
Event completion?
Timer?
```

Do not implement arbitrary batching until the scheduling contract is defined.
