# 1. 🎯 FINAL GOAL

PySkin ka ultimate goal ek **Python-first, low-latency reactive UI framework** banana hai.

Developer ko sirf Python likhna chahiye:

```python
import pyskin as ps

count = ps.State(0)

app = ps.Column(
    ps.Heading("Counter"),
    ps.Text(count),
    ps.Button(
        "+",
        on_click=lambda: count.set(count.value + 1)
    ),
)

ps.run(app)
```

```text
❌ HTML
```

`component()` now consults the registry:

```text

    ↓

```

However, current behavior intentionally keeps unknown props for backward compatibility.

Current:

```text
Known component
      ↓
Registry consulted              ✅
      ↓

```

This is acceptable for now.

Do **not** introduce strict prop rejection until the runtime contract is mature enough.

# 21. 🔥 CURRENT ARCHITECTURAL GAP

This is the most important point.

We currently have:

```text

 ↓

 ↓
WebSocket
 ↓
Browser
```

but the framework does not yet have the complete:

```text
State
 ↓
Dependency Graph
 ↓
Affected Components
 ↓
Dirty Nodes
 ↓
Minimal Diff
 ↓
Minimal Patch
```

Therefore PySkin currently proves:

> **How a known update can reach the browser.**

It does not yet fully prove:

> **How PySkin automatically determines the smallest possible update.**

That is the next major architecture.

```text
  ↓

  ↓
```

Target behavior:

```text
count.set(11)

```

# 23. 🔥 TASK 1 — DEFINE REACTIVE SEMANTICS

We need to formally decide:

```text
What does reactive=True mean?

What does reactive=False mean?

When is a State dependency registered?

When is a component subscribed?

When is an update generated?

When is an update suppressed?
```

Target:

```text
PropDefinition
      ↓
reactive=True
      ↓
runtime dependency participation
```

This should be a real runtime contract, not only metadata.

---

# 24. 🔥 TASK 2 — DEPENDENCY GRAPH

Target data model:

```text
State A
   │
   ├────► Component X
   │
   └────► Component Y

State B
   │
   └────► Component Z
```

Then:

```text
State A changes
       ↓
X + Y dirty
       ↓
Z untouched
```

This is the core of fine-grained reactivity.

---

# 25. 🔥 TASK 3 — DIRTY NODE TRACKING

Instead of rerendering everything:

```text
Application
    ↓
dirty set
```

Example:

```text
dirty_nodes = {
    "component_123",
    "component_456"
}
```

Only affected nodes should enter the update pipeline.

---

# 26. 🔥 TASK 4 — UPDATE SCHEDULER

Need a controlled scheduling layer:

```text
State changes
      ↓
mark dirty
      ↓
schedule update
      ↓
batch synchronous changes
      ↓
produce update
```

Example:

```python
count.set(1)
count.set(2)
count.set(3)
```

Potential target:

```text
3 separate network updates ❌
```

Instead:

```text
one scheduled update
final value = 3
```

This must be benchmarked rather than assumed.

---

# 27. 🔥 TASK 5 — DOM SEMANTICS

Current metadata supports:

```text
attribute
boolean
text
```

We eventually need a precise DOM semantic model:

```text
ATTRIBUTE
BOOLEAN ATTRIBUTE
DOM PROPERTY
TEXT CONTENT
CHILD NODE
```

For example:

```text
title
    → attribute

disabled
    → boolean attribute

value
    → potentially DOM property

text
    → text/content
```

This distinction becomes critical when generic patching grows.
